Dependency Inversion

Como fazer a regra de negócio mandar na infraestrutura, e não o contrário, para trocar banco, e-mail ou relógio sem tocar nas regras.

O problema

A regra "ao confirmar um pedido, salvar e avisar o cliente" é a parte que vale dinheiro. Mas, escrita de forma direta, ela cria o MySQL e o SMTP ali mesmo, dentro do método:

antes — a regra de negócio constrói a infraestrutura
class ConfirmarPedido:
    def executar(self, pedido):
        banco = mysql.connect(host="db.interno", user="app")   # a regra sabe o host
        banco.execute("UPDATE pedidos SET status='ok' WHERE id=%s", pedido.id)

        smtp = smtplib.SMTP("smtp.empresa.com")              # e o servidor de e-mail
        smtp.sendmail("loja@empresa.com", pedido.email, "Confirmado")

A regra mais importante do sistema depende de detalhes que mudam o tempo todo: onde está o banco, qual servidor de e-mail, qual biblioteca. Para testá-la, é preciso um MySQL e um SMTP de verdade. Trocar para PostgreSQL ou para um serviço de e-mail exige editar a regra, e o teste dela quebra por um motivo que não tem nada a ver com a regra.

A ideia

O princípio tem duas metades:

  1. Módulos de alto nível (a regra) não dependem de módulos de baixo nível (banco, e-mail). Os dois dependem de abstrações.
  2. As abstrações não dependem de detalhes; os detalhes dependem das abstrações.

Por isso "inversão": no código original, a seta de dependência vai da regra para o MySQL. Depois da inversão, o MySQL é que aponta para uma interface que a regra definiu. A regra passa a ser dona da interface, e a infraestrutura vira um plugin.

PeçaPapelNo exemplo
Alto nívelA regra, que decide o que precisaConfirmarPedido
AbstraçãoO que a regra precisa, nas palavras delaRepositorioDePedidos, Notificador
Baixo nívelO detalhe que implementa a abstraçãoRepositorioMySQL, NotificadorSmtp
Ponto de montagemO único lugar que conhece as duas pontasO main ou a configuração

Como fica

from typing import Protocol

# 1. as abstrações pertencem à regra, e usam o vocabulário dela
class RepositorioDePedidos(Protocol):
    def marcar_confirmado(self, pedido_id) -> None: ...

class Notificador(Protocol):
    def avisar(self, email, texto) -> None: ...

# 2. a regra recebe as dependências prontas, e não conhece nenhum detalhe
class ConfirmarPedido:
    def __init__(self, repositorio: RepositorioDePedidos, notificador: Notificador):
        self._repositorio = repositorio
        self._notificador = notificador

    def executar(self, pedido):
        self._repositorio.marcar_confirmado(pedido.id)
        self._notificador.avisar(pedido.email, "Confirmado")

# 3. os detalhes ficam de fora e apontam para as abstrações
class RepositorioMySQL:
    def marcar_confirmado(self, pedido_id): ...

# 4. o ponto de montagem: o único lugar que sabe quem é quem
caso_de_uso = ConfirmarPedido(RepositorioMySQL(), NotificadorSmtp())
// 1. as abstrações pertencem à regra, e usam o vocabulário dela
interface RepositorioDePedidos {
  marcarConfirmado(pedidoId: string): Promise<void>;
}

interface Notificador {
  avisar(email: string, texto: string): Promise<void>;
}

// 2. a regra recebe as dependências prontas, e não conhece nenhum detalhe
class ConfirmarPedido {
  constructor(
    private repositorio: RepositorioDePedidos,
    private notificador: Notificador,
  ) {}

  async executar(pedido: Pedido) {
    await this.repositorio.marcarConfirmado(pedido.id);
    await this.notificador.avisar(pedido.email, "Confirmado");
  }
}

// 3. os detalhes ficam de fora e implementam as abstrações
class RepositorioMySQL implements RepositorioDePedidos {
  async marcarConfirmado(pedidoId: string) { /* ... */ }
}

// 4. o ponto de montagem: o único lugar que sabe quem é quem
const casoDeUso = new ConfirmarPedido(new RepositorioMySQL(), new NotificadorSmtp());

O teste de ConfirmarPedido passa duas classes de cinco linhas, que guardam o que receberam em uma lista, e confere a lista. Sem Docker, sem rede, sem relógio, e roda em milissegundos.

Três coisas com nome parecido

Na conversa do dia a dia, estes termos se misturam, e vale separá-los:

NomeO que é
Dependency InversionO princípio: a regra define a abstração e os detalhes a implementam. É uma decisão de desenho
Dependency InjectionA técnica: receber a dependência de fora (construtor, parâmetro), em vez de criá-la dentro. É o jeito mais comum de aplicar o princípio
Container de DI / IoCUma ferramenta que faz a montagem automaticamente. Opcional: o main escrito à mão resolve a maioria dos projetos

É possível injetar sem inverter: se o construtor recebe RepositorioMySQL concreto, a dependência vem de fora, mas a seta continua apontando para o detalhe.

Como reconhecer a violação

SintomaO que está acontecendo
import de driver, SDK ou framework dentro do arquivo da regraA regra conhece o detalhe pelo nome
new / construtor de classe concreta dentro de método de negócioA regra decide qual detalhe usa, e não dá para trocar
datetime.now(), random(), os.environ no meio da regraAté o relógio e o ambiente são dependências escondidas, e tornam o teste instável
Teste unitário que usa patch("módulo.biblioteca") para tudoO teste precisa sabotar o código para escapar da dependência
Singleton ou variável global acessada de dentro da regraDependência escondida: a assinatura diz uma coisa, o corpo precisa de outra

Quando não aplicar

Cada inversão custa uma interface e um ponto de montagem. Ela se paga nas dependências que mudam, são lentas ou são difíceis de testar. As estáveis não precisam.

SituaçãoPor que nãoFaça isto
Biblioteca padrão estável: math, list, jsonNão muda e não tem efeito colateral; a abstração só adiciona ruídoUse direto
Script curto ou protótipoO ponto de montagem seria maior que o próprio códigoEscreva direto; inverta quando o primeiro teste doer
Classe de valor ou utilitário puro, sem I/ONada a trocar e nada a falsificarChame normalmente

Sinal de exagero: uma interface para cada classe, nomeada IAlgumaCoisa, com uma única implementação e um nome que só repete o da classe. Se a abstração não representa uma decisão da regra, é só uma cópia da classe.

Relação com os outros

O Adapter é o princípio aplicado quando a interface de fora não é a que a sua regra definiu: ele a traduz. O Strategy usa a mesma inversão para o algoritmo, e as fábricas resolvem o caso em que a regra precisa criar objetos sem conhecer a classe. E para que a abstração seja fácil de implementar, vale lembrar do Interface Segregation: pequena e feita para quem usa.
