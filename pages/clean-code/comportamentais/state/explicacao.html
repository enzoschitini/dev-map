Clean Code / Design Pattern / State

Explicação

Como fazer um objeto que se comporta de um jeito em cada fase da vida dele sem encher todos os métodos de if sobre em qual fase ele está.

O problema

Um pedido passa por fases: nasce como rascunho, é pago, é enviado, é entregue. Também pode ser cancelado, mas cancelar um rascunho não custa nada, cancelar um pedido pago exige estorno, e cancelar um pedido que já foi enviado nem é permitido.

A saída preguiçosa é guardar a fase em um texto e conferi-la dentro de cada método:

antes — a mesma escada de if em cada operação
class Pedido:
    def __init__(self):
        self.status = "rascunho"

    def pagar(self):
        if self.status == "rascunho":
            self.status = "pago"
        else:
            raise ValueError(f"não dá para pagar um pedido {self.status}")

    def enviar(self):
        if self.status == "pago":
            self.status = "enviado"
        else:
            raise ValueError(f"não dá para enviar um pedido {self.status}")

    def cancelar(self):
        if self.status == "rascunho":
            self.status = "cancelado"
        elif self.status == "pago":
            self._estornar()
            self.status = "cancelado"
        elif self.status in ("enviado", "entregue"):
            raise ValueError("o pedido já saiu; abra uma devolução")
        # e "cancelado"? cancelar de novo cai aqui sem fazer nada, e sem avisar

Três coisas quebram daqui a pouco. Uma fase nova, como "em separação", obriga a abrir todos os métodos e achar o lugar certo em cada escada. As regras de transição não estão em lugar nenhum: para saber de onde se chega a cancelado, é preciso ler o arquivo inteiro. E um erro de digitação em "enviado" não falha; só faz um if nunca ser verdadeiro.

A solução

Faça cada fase virar um objeto. O pedido guarda o objeto da fase atual e delega a ele o que fazer. Cada fase sabe o que permite, o que recusa e para qual fase o pedido vai depois. São quatro papéis:

PapelQuem éNo exemplo
ContextoO objeto que muda de comportamento; guarda o estado atual e delegaPedido
EstadoA interface: todas as operações que dependem da faseEstado
Estados concretosUma fase: o que ela permite, recusa e qual é a próximaRascunho, Pago, Enviado…
ClienteUsa o contexto, sem saber em que fase ele estáO checkout, a API

O ponto é para onde foi o if. Em vez de uma escada em cada método ("em qual fase estou?"), há uma escolha, feita uma vez, de qual objeto está ativo. O polimorfismo faz o resto. Uma operação que a fase não permite simplesmente não está implementada nela, e a recusa fica no padrão da interface.

Implementação

class TransicaoInvalida(Exception): ...

# 1. o estado: toda operação do pedido, recusada por padrão
class Estado:
    def pagar(self, pedido):    self._recusar("pagar")
    def enviar(self, pedido):   self._recusar("enviar")
    def entregar(self, pedido): self._recusar("entregar")
    def cancelar(self, pedido): self._recusar("cancelar")

    def _recusar(self, operacao):
        raise TransicaoInvalida(f"{operacao}, em {type(self).__name__}")

class TransicaoInvalida extends Error {}

// 1. o estado: toda operação do pedido, recusada por padrão
abstract class Estado {
  pagar(_: Pedido): void    { this.recusar("pagar"); }
  enviar(_: Pedido): void   { this.recusar("enviar"); }
  entregar(_: Pedido): void { this.recusar("entregar"); }
  cancelar(_: Pedido): void { this.recusar("cancelar"); }

  private recusar(operacao: string): never {
    throw new TransicaoInvalida(`${operacao}, em ${this.constructor.name}`);
  }
}

// 2. os estados concretos: cada um só escreve o que permite
class Rascunho extends Estado {
  override pagar(p: Pedido)    { p.irPara(new Pago()); }
  override cancelar(p: Pedido) { p.irPara(new Cancelado()); }
}

class Pago extends Estado {
  override enviar(p: Pedido) { p.irPara(new Enviado()); }

  override cancelar(p: Pedido) {
    p.estornar();
    p.irPara(new Cancelado());
  }
}

class Enviado extends Estado {
  override entregar(p: Pedido) { p.irPara(new Entregue()); }
}

class Entregue extends Estado {}
class Cancelado extends Estado {}

// 3. o contexto: guarda o estado atual e delega
class Pedido {
  private estado: Estado = new Rascunho();

  irPara(estado: Estado) { this.estado = estado; }
  estornar() { /* … */ }

  pagar()    { this.estado.pagar(this); }
  enviar()   { this.estado.enviar(this); }
  entregar() { this.estado.entregar(this); }
  cancelar() { this.estado.cancelar(this); }

  get status() { return this.estado.constructor.name.toLowerCase(); }
}

// 4. o cliente: pede a operação, sem perguntar em que fase está
const pedido = new Pedido();
pedido.pagar();
pedido.cancelar();   // estorna, porque está em Pago

O teste de uma fase é uma classe e uma chamada: Pago().enviar(pedido) e confira para onde o pedido foi. Uma fase nova, como "em separação", é uma classe nova e uma linha em Pago que aponta para ela; nenhuma outra fase é aberta.

Quando usar

O State vale quando três coisas acontecem ao mesmo tempo: o comportamento do objeto depende de uma fase que muda ao longo da vida dele; há várias fases, cada uma com comportamento próprio; e a pergunta "em que fase estou?" aparece em mais de um método.

Na prática, isso aparece no código de algumas formas reconhecíveis:

SituaçãoComo reconhecer no códigoExemplo
A mesma escada de if sobre a fase em vários métodosif self.status == … / elif repetido no começo de cada operação, como o pagar e o cancelar acimaO exemplo desta página
O mesmo gesto faz coisas diferentes conforme o modoswitch (ferramenta) dentro de cada um dos handlers de mouse ou de tecladoUso #1
Flags booleanas que juntas descrevem a faseself.aberto, self.meio_aberto e self.falhas, em que algumas combinações não deveriam existirUso #2
Algo precisa acontecer toda vez que se entra ou se sai de uma faseUm timer.cancel() ou uma limpeza copiada em cada método que muda status, e esquecida em umUso #3
As transições não estão escritas em lugar nenhumPara descobrir de onde se chega a cancelado, é preciso ler todos os métodosO exemplo desta página

O que os sinais têm em comum: a pergunta "em que fase estou?" é feita por quem não deveria precisar fazê-la. O State é o lugar para onde a resposta se muda, para os métodos só pedirem a operação.

Um teste rápido

Na dúvida, responda em ordem. A primeira resposta que manda parar decide.

  1. O objeto muda de comportamento ao longo da vida? Se ele se comporta sempre do mesmo jeito, não há fase para modelar.
  2. Há mais de duas ou três fases? Com duas, um booleano e um if resolvem, e as classes não se pagam.
  3. A diferença aparece em mais de uma operação, ou há algo a fazer ao entrar e sair? Se só uma decisão depende da fase, um if naquele ponto basta.
  4. Cada fase tem um comportamento próprio, e não só "pode" ou "não pode"? Se a fase só decide quais transições valem, uma tabela de transições é mais curta. O State vale quando há o que fazer.

Quando não usar

O custo do State é uma classe por fase, e o fluxo inteiro deixa de caber em uma tela. As transições ficam espalhadas, cada uma dentro da fase de onde sai, então ver o "diagrama" de estados exige abrir várias classes. Com muitas fases pequenas, o objeto se pulveriza em arquivos de três linhas, e o ganho de clareza some.

SituaçãoPor que nãoFaça isto
Duas fases (ligado e desligado, aberto e fechado)Duas classes para um booleanoUm bool e um if
As fases só definem quais transições são válidasNão há comportamento por fase, só permissãoUm enum e um dicionário de transições
A fase é só um rótulo para exibirNada muda no comportamento em função delaUm campo status
O comportamento é escolhido de fora, e não muda por transiçõesO que varia é o algoritmo, não a fase de vidaStrategy
Fluxo longo, com muitas transições, ou vindo de configuraçãoAs classes viram uma máquina de estados escrita à mãoUma biblioteca de máquina de estados ou de workflow

Sinais de que o State saiu do lugar

  • O cliente pergunta a fase. Um if pedido.status == "pago" antes de chamar cancelar() traz a escada de volta, agora fora do objeto, e as duas regras divergem.
  • Os estados vazios. Classes com pass em tudo, diferentes só pelo nome, mostram que um enum bastava.
  • As fases se conhecem em malha. Cada estado cria os outros estados concretos, e acrescentar uma fase obriga a abrir várias. Se isso dói, centralize as transições.
  • O estado copia dados do contexto. Campos duplicados entre o estado e o pedido saem de sincronia. O estado deve guardar só o que é dele.
  • Transições sem evento. Um estado que decide sozinho, sem que ninguém peça, para onde ir é uma máquina que roda por conta própria e ninguém sabe quando.

O sinal mais comum: o if pedido.status == … reaparece na tela e na API, para decidir o que oferecer. O estado deixou de ser a única fonte de verdade, e a regra de "o que vale agora" passa a existir em três versões.

Na dúvida, comece com um enum e um if. Extraia os estados quando a segunda ou a terceira operação precisar da mesma escada: nesse ponto as fases já existem no código, e é só dar a cada uma um nome e um lugar.

Parecidos

PadrãoDiferença
StrategyTem a mesma forma (um contexto delega a um objeto trocável), mas quem troca é o cliente, de fora, e as opções não se conhecem. No State, o próprio objeto troca de fase, e cada fase sabe qual é a próxima
ObserverAvisa quem estiver interessado de que a fase mudou. O State é quem decide o que fazer em cada fase, e os dois aparecem juntos
MementoGuarda os dados de um objeto para voltar a eles depois. O State guarda comportamento; não guarda uma foto
Máquina de estados em tabelaNão é do catálogo GoF: um enum e um dicionário de transições. Serve quando as fases só definem o que é permitido, sem comportamento próprio

Regra prática: se o objeto troca sozinho de objeto de comportamento, conforme a vida dele avança, é State. Se alguém de fora escolhe qual objeto usar, é Strategy.
