Clean Code / Design Pattern / Template Method

Explicação

Como escrever uma vez só a ordem dos passos de um processo, e deixar cada variação preencher apenas o passo que é diferente dela.

O problema

A loja importa catálogo de fornecedores. O primeiro manda CSV; o segundo, JSON. O roteiro é o mesmo nos dois: ler o arquivo, conferir os preços, gravar tudo em uma transação e registrar o que entrou. Só a leitura é diferente.

A saída preguiçosa é copiar a primeira função e trocar o miolo:

antes — o roteiro copiado, e já divergindo
def importar_csv(caminho):
    with open(caminho, newline="") as f:
        produtos = [Produto(l["sku"], Decimal(l["preco"])) for l in csv.DictReader(f)]
    for p in produtos:
        if p.preco <= 0:
            raise ImportacaoInvalida(p.sku)
    with db.transacao():
        for p in produtos:
            db.salvar(p)
    log.info("importados %d produtos", len(produtos))

def importar_json(caminho):
    with open(caminho) as f:
        itens = json.load(f)["itens"]
    produtos = [Produto(i["codigo"], Decimal(str(i["valor"]))) for i in itens]
    for p in produtos:
        if p.preco <= 0:
            raise ImportacaoInvalida(p.sku)
    for p in produtos:          # a transação ficou para trás
        db.salvar(p)
    log.info("importados %d produtos", len(produtos))

Três coisas quebram daqui a pouco. As duas cópias já divergiram: a do JSON grava sem transação, e uma importação que falha no meio deixa o catálogo pela metade. Um terceiro formato é a terceira cópia, com a terceira chance de esquecer algo. E qualquer regra nova (rejeitar SKU repetido, por exemplo) é uma edição em cada função, sem nada que avise quando uma ficar de fora.

A solução

Escreva o roteiro uma vez, em uma classe base, e deixe os passos que variam como buracos para as subclasses preencherem. Quem chama é a classe base: ela decide a ordem e, em cada ponto, pergunta à subclasse o que fazer. São quatro papéis:

PapelQuem éNo exemplo
Classe baseDona do roteiro e dos passos que são iguais para todosImportador
Método-templateO método que fixa a ordem dos passosimportar()
Passo variávelO buraco: obrigatório, ou com um padrão que pode ser trocadoler(), validar()
Subclasse concretaPreenche só o que é diferente delaImportadorCsv, ImportadorJson

O ponto é a direção da chamada: o pai chama o filho, e não o contrário. A subclasse nunca decide quando seu passo roda nem o que vem antes ou depois dele. Por isso a transação, a ordem e o log não dependem de ninguém lembrar deles.

Implementação

from abc import ABC, abstractmethod

# 1. a classe base: dona do roteiro
class Importador(ABC):

    # 2. o método-template: a ordem dos passos, escrita uma vez
    def importar(self, caminho):
        produtos = self.ler(caminho)
        self.validar(produtos)
        with db.transacao():
            for produto in produtos:
                db.salvar(produto)
        log.info("importados %d produtos", len(produtos))

    # 3. o passo que muda: a subclasse é obrigada a escrever
    @abstractmethod
    def ler(self, caminho) -> list[Produto]: ...

    # 4. um passo comum, com padrão que a subclasse pode trocar
    def validar(self, produtos):
        for p in produtos:
            if p.preco <= 0:
                raise ImportacaoInvalida(p.sku)

# 5. as subclasses: só o que é diferente
class ImportadorCsv(Importador):

// 1. a classe base: dona do roteiro
abstract class Importador {

  // 2. o método-template: a ordem dos passos, escrita uma vez
  async importar(caminho: string) {
    const produtos = await this.ler(caminho);
    this.validar(produtos);
    await db.transacao(async () => {
      for (const produto of produtos) await db.salvar(produto);
    });
    console.log(`importados ${produtos.length} produtos`);
  }

  // 3. o passo que muda: a subclasse é obrigada a escrever
  protected abstract ler(caminho: string): Promise<Produto[]>;

  // 4. um passo comum, com padrão que a subclasse pode trocar
  protected validar(produtos: Produto[]) {
    for (const p of produtos) {
      if (p.preco <= 0) throw new ImportacaoInvalida(p.sku);
    }
  }
}

// 5. as subclasses: só o que é diferente
class ImportadorCsv extends Importador {
  protected async ler(caminho: string) {
    const linhas = await lerCsv(caminho);
    return linhas.map(l => new Produto(l.sku, Number(l.preco)));
  }
}

class ImportadorJson extends Importador {
  protected async ler(caminho: string) {
    const dados = JSON.parse(await readFile(caminho, "utf8"));
    return dados.itens.map((i: any) => new Produto(i.codigo, i.valor));
  }
}

await new ImportadorJson().importar("fornecedor-b.json");

O roteiro agora se testa uma vez, com uma subclasse de cinco linhas cujo ler devolve uma lista fixa: confira que a transação envolve a gravação e que um preço zero aborta antes. Cada ler se testa sozinho, com um arquivo pequeno. Um formato novo é uma classe com um método.

Quando usar

O Template Method vale quando três coisas acontecem ao mesmo tempo: existem duas ou mais variantes do mesmo processo; a ordem dos passos é a mesma em todas; e o que muda cabe em poucos passos bem nomeados, enquanto o resto é igual.

Na prática, isso aparece no código de algumas formas reconhecíveis:

SituaçãoComo reconhecer no códigoExemplo
Funções quase iguais, com um miolo diferenteDuas funções com 80% das linhas iguais; uma correção feita em uma delas e esquecida na outraUso #1
Um passo que nenhuma variante pode pularverificar_assinatura() repetido em cada handler (e faltando em um); um try/finally copiadoUso #2
A política do processo varia pouco, de forma pontualif self.ativo:, parâmetros antes=None, depois=None ou comentários "este job pula fim de semana"Uso #3
O mesmo roteiro com um tipo novo à vistaUm if tipo == … em cada passo do mesmo processoUso #1

O que os sinais têm em comum: você encontra o mesmo esqueleto escrito mais de uma vez, e a diferença entre as cópias é pequena e fácil de apontar. Se for difícil dizer "o que muda é só isto", ainda não há um template.

Um teste rápido

Na dúvida, responda em ordem. A primeira resposta que manda parar decide.

  1. Existe mais de uma variante do processo? Se só há uma, escreva uma função. Ainda não há o que separar.
  2. A ordem dos passos é a mesma em todas? Se a ordem muda de uma variante para outra, o esqueleto não é fixo: escreva cada fluxo, ou componha os passos de fora.
  3. O que varia cabe em um ou três passos? Se quase tudo muda, sobra um esqueleto fino demais para valer uma classe base.
  4. Dá para passar o passo como função? Se o que varia é uma ação sem estado, passe uma função como parâmetro. Herança só se paga quando as variantes têm vários passos e dados próprios.

Quando não usar

O custo do Template Method é a herança. A subclasse fica presa à classe base: qualquer mudança no esqueleto atinge todas, e o fluxo fica dividido em dois arquivos, de modo que, para saber o que acontece, é preciso abrir o pai e o filho. Cada hierarquia ainda varia em uma dimensão só.

SituaçãoPor que nãoFaça isto
Há uma variante só, sem segunda à vistaA classe base nasce sem ter o que compartilharUma função. Extraia a classe base quando a segunda variante aparecer
O que varia é um passo único e simplesUma hierarquia para uma ação é cerimôniaPasse uma função como parâmetro
A variação precisa mudar em tempo de execuçãoA herança é fixada quando o objeto é criadoStrategy: guarde o passo como objeto e troque-o
Duas coisas variam de forma independente (formato e destino)A herança explode em uma subclasse por combinaçãoComposição, ou Bridge
A ordem dos passos muda entre as variantesO método-template deixa de ser um esqueleto e vira um if disfarçadoEscreva cada fluxo, ou monte a sequência fora, como dados
Só abrir e fechar um recurso em volta de um trechoÉ um roteiro de dois passoswith / try/finally

Sinais de que o Template Method saiu do lugar

  • A subclasse sobrescreve o próprio roteiro. Se importar é redefinido, o esqueleto deixou de garantir qualquer coisa: cada subclasse tem o seu, e a garantia voltou a depender de cada autor.
  • Ganchos demais. Doze pontos de extensão, cada um com um padrão, e ninguém sabe qual sobrescrever. Cada gancho é uma promessa que a classe base precisa manter para sempre.
  • Passos que viram pass. Se várias subclasses implementam um passo abstrato com pass ou levantando NotImplementedError, o esqueleto não serve para todas.
  • "Lembre de chamar super()." O passo só funciona se a subclasse chamar o pai na hora certa. Esse contrato fica na cabeça de quem escreve, não no código.
  • Hierarquia em três níveis. A classe do meio redefine parte do roteiro e os netos redefinem outra parte. Ninguém sabe mais em que ordem as coisas rodam.

O sinal mais comum: subclasses que sobrescrevem o método-template inteiro "só desta vez". Python e TypeScript não têm final para impedir; proteja com um teste que falhe se alguma subclasse redefinir o roteiro, ou com uma convenção que a revisão de código cobre.

Na dúvida, comece com uma função que recebe os passos que mudam como parâmetros. Quando as variantes ganharem estado próprio e vários passos, a classe base se paga, e a refatoração é pequena porque o roteiro já está escrito em um lugar.

Parecidos

PadrãoDiferença
StrategyTroca o algoritmo inteiro por composição, até em tempo de execução. O Template Method fixa o esqueleto e varia as partes por herança, no momento em que a classe é escrita
Factory MethodÉ um Template Method especializado em um passo só: criar o objeto. O roteiro usa o que a subclasse criou
DecoratorAcrescenta comportamento em volta de um objeto, por composição, sem herdar. No Template Method o pai chama a subclasse no meio do roteiro
ObserverAvisa vários ouvintes que não podem mudar o fluxo; o gancho do Template Method é uma subclasse só, que preenche (e às vezes altera) um passo do roteiro

Regra prática: se o esqueleto é herdado e os passos são métodos que o pai chama, é Template Method. Se o algoritmo é um objeto que se passa de fora, é Strategy.
